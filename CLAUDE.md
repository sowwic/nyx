# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Nyx is a Python nodal execution graph: a PySide6 editor plus a headless runner. Python is pinned to `==3.14.3`; dependencies are managed with `uv`.

## Commands

The Makefile includes shared targets from `.make/` (fetched from `sowwic/makefiles`; `make update-make` refreshes them).

```sh
uv sync --locked --dev                     # install
make pytest                                # uv run pytest tests
uv run pytest tests/core/test_node.py::test_name   # single test
make pytest-pdb                            # drop into pdb on failure
make lint | lint-fix | format              # ruff (line length 89, rules E, F, UP)
make check                                 # lint + tests
make qrc                                   # regenerate resources_rc.py (needed after editing .qrc files or icons/fonts)
make mkdocs                                # docs dev server
nyx                                        # open the editor
nyx stage run path/to/stage.nyx            # run a stage headless (same as nyx-run-stage)
```

`stage run` flags: `--no-bridge`, `--port N`. Exit codes: `0` ran, `1` failed, `2` file not found or unloadable.

`resources_rc.py` files are generated by `pyside6-rcc` for both `src/nyx/resources` and `src/nyx/stdlib/resources`; `qrc` is also a prerequisite of `make build`.

### Tests

- `tests/conftest.py` sets `QT_QPA_PLATFORM=offscreen`; `tests/editor` tests start the editor app (pytest-qt).
- The `with_plugins(*plugin_ids)` marker initializes the given plugins for a test.
- Coverage (`--cov=nyx`) is always on; the `output_dir` fixture writes under `test_output/`.
- CI runs Linux and Windows first, then macOS (skipped for draft PRs).

## Architecture

- **`nyx.core`** is the Qt-based backend (no widgets). A `Stage` owns a `QUndoStack` and holds `Node`s, each with `NodeComponent`s connected by `Link`s, plus `UtilObject`s (groups, notes). Every mutation is a `QUndoCommand` in `core/commands/` derived from `NyxCommand`: the stage is held weakly, `target_nodes` lets the stage refuse changes to nodes of a reference node, and `MODIFIES_STRUCTURE` marks commands that add, remove or redefine nodes or components. Execution lives in `execution_chain.py`, `stage_crawler.py` and `contexts/`.
- **`nyx.api.v1`** is the public API. Plugins and the stdlib import from here, not from `nyx.core`.
- **Plugins** (`core/plugin_subsystem/`): `PluginLoader` discovers `nyx_plugin.py` files in the stdlib, `nyx/plugins/functions/*`, the `plugin_paths` config value and the `NYX_PLUGIN_PATH` env var. A `NyxPlugin.initialize` fills `NyxPluginContents` (nodes, components, datatypes, util and graphics objects; `register_function_node` wraps a plain function as a node), and everything ends up in `NYX_REGISTRY`. `nyx.stdlib` is the core plugin the others rely on; its nodes and components are all registered there.
- **Session and config**: `NyxSession` holds the config, open stages and the bridge server. `NyxConfig` is a `json_config` `LayeredConfig`; its typed values are in `core/config_values/`. `get_app_config()` returns the running app's config.
- **Bridge**: `NyxSession` runs a TCP `BridgeServer` so external processes (Maya, Blender, ...) can run code for Remote Client and Remote Action nodes. The protocol is the separate `nyx-bridge` repo and the DCC plugins live in their own repos. `json-config`, `json-config-qt` and `nyx-bridge` are git dependencies pinned by tag in `pyproject.toml`.
- **Startup hooks**: `NyxApplication.__init__` registers the builtin content, calls `pre_initialize()`, loads plugins, then calls `post_initialize()`. Subclasses override the hooks to run code at those points; `NyxEditorApplication` shows the startup splash in `pre_initialize` (the plugin log messages need it up before loading) and builds the QML engine and main window in `post_initialize`. Don't work around the order with flags such as `initialize_plugins=False` followed by a manual call in the subclass `__init__`; that duplicates the base startup sequence.
- **`nyx.editor`**: widgets, the QGraphics scene (`graphics/`), views, and QML UI (`editor/qml/NyxEditor`, `stdlib/qml/NyxStdlib`, each with a `qmldir`). Editor actions go through `core/action_registry.py` and `action_router.py`. `application.py` has `NyxApplication` (usable without the editor window) and `NyxEditorApplication`.
- **Paths**: `nyx/static/paths.py` defines all user files (config, last session, bridge address file, logs, profiling) from a single `platformdirs` data dir.

## Conventions

- Google-style docstrings (`Args:`, `Returns:`, `Raises:`).
- Prefer flexibility: when a subclass or plugin needs to run code at a point inside a base class's sequence (before or after a step), add an overridable hook (`pre_*` / `post_*`, a no-op in the base class) rather than changing constructor arguments, reordering the subclass `__init__` around `super().__init__`, or copying the base sequence. Example: `NyxApplication.pre_initialize` / `post_initialize` for the editor splash screen.
- `develop` is the default and PR branch; `main` is the release branch. `VERSION` is the version source (`make update-version` syncs `pyproject.toml`). Record user-visible changes in `CHANGELOG.rst`.

## Development

- If the current branch is `develop`, ask the user for the GitHub issue number before starting work. Use related branch
- Do not commit unless asked to.
- Do not update CHANGELOG unless asked to
- Do not push extra created worktrees to remote. Once work in them is done - patch it back into feature branch and delete extra worktree created.
- When a task done in a worktree is finished, do this without being asked: exit the worktree (`ExitWorktree` keep), cherry-pick its commit(s) onto the feature branch in the main checkout, then remove the worktree and its branch. Git can't reach the main checkout from inside the worktree session.

## Docs images

Only when a docs update is requested.

- The built-in types have a page each: `docs/user/stdlib/{nodes,components,util-objects}/<name>.md`, where `<name>` is the type id without its namespace and with `_` replaced by `-` (`core:for_loop` is `for-loop`). A page starts with `![Title](../../../_static/images/stdlib/<kind>/<name>.png)`. A new built-in type also needs a row in the `index.md` of its folder and an entry in the `mkdocs.yml` nav.
- Render these images with `scripts/docs_images.py`, don't screenshot by hand or leave placeholders: `uv run python scripts/docs_images.py` for all, or `graph` (nodes and util objects) / `components`. It overwrites the files of the same names in `docs/_static/images/stdlib/`. `--out DIR` writes elsewhere, to compare first.
- Nodes and util objects are crops of the graph scene. Components are their item in the Inspector, fully expanded with the Links section; the script enables a socket on the added component because that section is hidden without one, and sets the dark palette on the Inspector because the offscreen platform leaves the text dark on dark.
- A new kind of image or a change to how a type is drawn goes into the script. Read a few of the results to check them. The look follows the editor config of whoever runs it, nothing is saved to it.
- Other images (`editor_preview.png`, ...) are made by hand and live in `docs/_static/images/`.

## Qt Notes

### QWidgets

New QWidgets should follow the following architecture unless it causes issues.

Methods:

- _create_actions - creates actions and configures them
- _create_widgets - creates child widgets and configures them
- _create_layouts - creates layouts, populates them with widgets
- _create_connections - creates signal-slot connections
- Above methods are run in **init**

## Verifying UI work cheaply

- Check state, not pixels, by default: over MCP `execute_python`, read attributes (`ops.getAttr`), widget state (find widgets by class and read text, checked state, enabled, items) and command results. Assert the numbers.
- Take a screenshot (`captureView`, or a widget grab) only where the visual result is the point: viewport drawing, layout, styling, icons. One capture at the end of a check, not one per step.

## Token hygiene

- Find symbols with the LSP tool if possible before grepping; then Read with offset/limit.
